# Security

vauly is built so that the server holding your data can't read it. This page describes how, what the server can still see, and where the model stops protecting you. [Threat model](threat-model.md) lists who vauly protects against and where its parts trust each other. To report a vulnerability, see [SECURITY.md](../SECURITY.md).

## Goals

- Someone with the database, or full control of the API, learns no passwords, item names or item contents from what it stores. [Limits](#limits) says where that ends: the server delivers the web app, and hands out the public keys that vaults and items are shared to.
- Your master password never leaves your device, so the server can't leak it.
- People only open the vaults that were shared with them, enforced by cryptography as well as by the API.
- Scripts and agents get the values they're allowed to use, inside the command they run, and nothing else.

## Keys

All cryptography is implemented once, in [`packages/crypto`](../packages/crypto/src/index.ts), and used by the web app, the browser extension and the CLI. It's WebCrypto, except for Argon2id, which comes from [libsodium](https://doc.libsodium.org/) ([`argon2.ts`](../packages/crypto/src/argon2.ts)).

<!-- diagram: KeyChain -->

```
master password ──Argon2id, 64 MiB, 3 passes, 1 lane, 16-byte salt──▶ master key
                  (accounts from before Argon2id: PBKDF2-SHA256, 600,000 rounds, until they move)
master key ──HKDF-SHA256 "vauly/auth"──▶ auth key  (256 bits, sent to sign in)
master key ──HKDF-SHA256 "vauly/wrap"──▶ wrap key  (AES-256-GCM, never leaves the device)

account key pair   ECDH P-256; the private key is sealed with the wrap key
vault key          AES-256-GCM, one per vault, wrapped to each member's public key
item key           AES-256-GCM, one per item, wrapped with its vault key
file key           AES-256-GCM, one per attached file, sealed with its item key
```

- **Signing in.** The browser asks for your salt and key derivation settings, derives the auth key and uses it as the password for the session. The server stores only a hash of the auth key (Better Auth's default, scrypt). For an email it doesn't know, the server returns a stable made-up salt, so the sign-in page doesn't reveal who has an account.
- **Unlocking.** The wrap key opens your private key. With it the browser unwraps the keys of your vaults, then the keys of their items. All of these stay in memory: reloading the page, choosing **Lock now** or staying idle (15 minutes by default, set per device) forgets them. The session cookie alone opens nothing. A device can also unlock with a passkey instead of the master password; see [Unlocking with a passkey](#unlocking-with-a-passkey).
- **Encryption.** Every encrypted value is AES-256-GCM with a fresh random 12-byte IV, stored as `base64(iv).base64(ciphertext)`.
- **Files.** A file attached to an item is encrypted in the browser before it's uploaded, a chunk of 1 MiB at a time, with a key of its own. That key, the file's name and its type are sealed with the item key, so anyone who can open the item can open its files, and nobody else. Each chunk names its file, its place and how many there are, so the server can't reorder, drop or swap chunks without the download failing. The server sees each file's size, which item it's on and who added it. Share links don't carry files. An agent gets an item's files only when a reference names one and the approval said so, and only the files the item had then; files added later need another approval. It downloads them with passes that name the agent, the grant and the file and last 15 minutes, signed with a key the server derives from its secret for passes alone, and the server checks the grant again on every download, so revoking it ends them.
- **Sharing.** To give someone a vault, the browser wraps the vault key to their public key: an ephemeral ECDH P-256 key pair, HKDF-SHA256 bound to the recipient's public key, then AES-256-GCM. Only their private key can open it.
- **Roles in a vault.** Each person can view, edit or manage a shared vault. The server enforces the role: it refuses changes to items, share links and agent access from someone who can only view, and changes to who can open the vault from anyone but its managers. Viewers don't see the vault's share links, agents' requests and grants, or their activity: a link's ID alone would let them use up a one-view link. A vault always keeps a manager; changes that would remove the last one are refused in the same database statement that makes them. Cryptography can't make the difference, since reading a vault takes its key, and the key would let someone encrypt new items too. A viewer who wanted to could keep what they read, as anyone with access could.
- **Two-step login.** Someone who turns it on must give a six-digit code (RFC 6238: SHA-1, 30 seconds) after their password checks out. The server checks the code, so it keeps the setup key; it accepts one step of clock drift either way and never the same step twice. Without a valid code, the session the password just created is deleted before it's returned. Turning it on signs out your other sessions, since they gave the password alone; it takes effect only if two-step login is still off and the setup key is still the one the code came from, so of two setups at once, one wins. An admin's reset signs the member out everywhere. Ten recovery codes, 50 random bits each, are shown once and stored as SHA-256 hashes; each works once. The web app and the browser extension send the code the same way, in an `x-vauly-code` header. Two-step login guards signing in only: it adds nothing to encryption, which rests on the master password, and, on a device where you turn it on, on a passkey there too (see [Unlocking with a passkey](#unlocking-with-a-passkey)).
- **Limits on tries.** Counts slow down anyone who guesses:
  - **Per address.** Better Auth's routes count requests by the client's address as Cloudflare gives it (`CF-Connecting-IP`), each route apart; an IPv6 address counts with the rest of its /64. Sign-in takes a run of ten tries, then refuses with a 429 until a minute has passed since the last one it took: that's for guessing across accounts, and a team behind one office address shouldn't reach it. Most other routes take a hundred requests in ten seconds; Better Auth holds a few that vauly doesn't use to less. Everyone behind one address counts as one, as behind a home router or a mobile carrier, and so do requests that reach the Worker from another Cloudflare Worker. Only the routes Better Auth serves under `/api/auth` are counted this way, so a request for any other path writes no count. The counts are in the database, so every instance of the Worker shares them; a row is deleted after a minute, once some later request starts a new count. A request with no address of its own, which happens only outside Cloudflare, as in local development, isn't counted, and the Worker logs a warning the first time one comes without the header.
  - **Per account.** Codes and master passwords count too, in two counts. One is two-step codes at sign-in. The other is the checks inside a session: the codes that turn two-step login on and off, and the master password the server checks before it changes it, moves its keys to Argon2id or deletes the account. After three wrong ones in a row, the next try waits five seconds, then twice as long after each wrong one, up to five minutes. A try that comes too soon isn't checked, and a right one starts its count again. Nothing locks an account. Only someone past its master password can add to the sign-in count, and someone who keeps guessing codes can keep the next sign-in waiting; a session that's already open isn't held up, and changing the master password from it ends their guessing and clears the count. An admin's reset of someone's two-step login clears both counts.
- **Requiring two-step login.** An owner or admin can require it for everyone, in **Settings › Workspace**, once they have it themselves. While it's on, the server refuses a member without it on every route but the few that setting it up needs: their profile, the two setup steps, and turning off this device's notifications. Unlocking comes after the setup, so moving their keys to Argon2id and a passkey's unlock wait for it too. It refuses with a 403 that says why, never a 401, so they stay signed in to set it up. The web app shows the setup in place of the app, before unlock, and the browser extension says the same and opens the web app. A test walks every route in the API: each one is on a short list of public routes, or of agents' routes, which take an agent's token and refuse a member's session, or of those few; every other one must be refused, and is, so a route added later is refused unless someone adds it to a list. While it's required, nobody can turn their own two-step login off. Agents keep working: they use their token, not a member's sign-in. Turning it on and off, and each setup, is in the activity log.
- **Changing the master password** derives new keys with Argon2id from a fresh salt and seals the same private key with the new wrap key. The server swaps the auth hash and the sealed key in one batch, if nothing else changed them since you began, and signs out your other sessions. Your key pair, and so your access to shared vaults, stays the same.

## Key derivation

Every master password goes through Argon2id: 64 MiB of memory, three passes and one lane, which is RFC 9106's second recommendation with one lane instead of four. A browser runs the lanes one after another, so more of them would cost the device time and an attacker nothing. Deriving the key takes about 0.15 seconds on a recent laptop, and under a second on a processor four to six times slower, like a budget phone's.
- **Where it runs.** Argon2id is libsodium's WebAssembly build, pinned to one version. WebAssembly needs `'wasm-unsafe-eval'` in a Content-Security-Policy, and the app's pages don't have it. So in the web app it runs in a key worker: browsers apply the worker script's own policy to a worker, not the page's, and the worker's files are served with `default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; base-uri 'none'; frame-ancestors 'none'`. The worker can compile WebAssembly but can't connect anywhere, and the page still can't compile it. In the iPhone app, whose files come with no headers, the worker has no policy of its own and runs only the app's files ([The app for iPhone](#the-app-for-iphone)). Each derivation ends its worker, freeing the 64 MiB, and a fresh one waits for the next; one that doesn't answer within a minute is ended too. The extension's pages, which load only its own files, allow WebAssembly in its manifest.
- **What a server can ask for.** The server sends the settings with the salt, so a compromised one could ask for less work and then test guesses against the auth key it gets back. The apps refuse to derive below PBKDF2 at 600,000 rounds, or Argon2id at 19 MiB and two passes (OWASP's minimums), above 1 GiB or ten passes, which could exhaust a phone's memory, or with a salt that isn't 16 bytes. The server accepts nothing outside those limits either. Once a device has seen an account use Argon2id, it refuses PBKDF2 for that account from then on, so a server can't quietly move it back. (If you restore a database backup from before an account moved, its devices refuse it until their site data, or the extension's, is cleared.)
- **Apps from before Argon2id** read only `kdfIterations`, which stays at PBKDF2's 600,000 for Argon2id accounts; the passes are in `kdfPasses`. Such an app derives a PBKDF2 key, slowly, and fails to sign in, rather than send the server something cheap to test guesses against. Update the browser extension with the server.
- **Accounts from before Argon2id** used PBKDF2-SHA256 with 600,000 rounds. The next time someone signs in or unlocks with their master password in the web app, it moves their account, after the vault has opened. It derives Argon2id keys from a fresh salt, seals the same private key with the new wrap key, and opens that copy again from scratch to check it before sending it. The server swaps the auth hash and the sealed key in one batch, as for a new password, but keeps your other sessions, since the password hasn't changed. It does that once, while the account is still on PBKDF2. Both this swap and a password change happen only if the keys are still the ones the request started from, checked in the same batch, so of two at once (two devices moving it, or a move and a password change), one wins and the other is refused and changes nothing. If the reply to a move is lost, the account has moved anyway, and the next unlock sees that. Devices that still hold the old settings keep unlocking with them, since they open the same key pair, until they next load the account. The demo's shared account doesn't move: it goes back to how it was every hour. Rolling a server back to a version from before Argon2id strands accounts that moved, which can't sign in until it rolls forward again.
- **Files other apps protect.** vauly opens Bitwarden's password-protected export, Proton Pass's PGP-encrypted export and KeePass databases in the browser, with the password you type. Neither the password nor what it opens is sent anywhere or kept.
  - **Bitwarden.** The key is PBKDF2-SHA256, or Argon2id from hash-wasm, pinned to one version. Bitwarden's Argon2id defaults to four lanes and libsodium's has one. Like libsodium, hash-wasm runs only in workers served from the key worker's folder, and only for these files and vauly's own protected backups; the keys to your account never come from it.
    - The salt is the base64 text in the file, taken as UTF-8, not the bytes it encodes. Argon2id takes its SHA-256.
    - HKDF-Expand alone, with no extract step, turns the 32 bytes into an AES-256-CBC key and an HMAC-SHA256 key, with the infos "enc" and "mac".
    - The MAC is checked before anything is decrypted.
    - The file sets the work, so vauly refuses what Bitwarden's own import refuses: PBKDF2 outside 5,000–2,000,000 rounds, or Argon2id outside 2–10 passes, 16–1024 MiB and 1–16 lanes.
  - **Proton Pass.** The file is symmetric OpenPGP with an iterated and salted S2K. vauly decrypts it with OpenPGP.js, which loads only for these files.
    - It takes only what Proton makes: one passphrase packet, with that S2K, and no packet for a key.
    - Anything else is refused before the passphrase is tried. OpenPGP.js would hash for every passphrase packet at once, as much as each asks, on the page's thread.
    - The file may unpack to at most 256 MiB.
  - **KeePass.** A `.kdbx` database, KDBX 3.1 or 4, opens in an import worker of its own, served from the key worker's folder with its policy, so it can compile WebAssembly and can't connect anywhere; in the iPhone app it has no policy of its own, as the key worker hasn't. It reads the format with [kdbxweb](https://github.com/keeweb/kdbxweb) 2.1.1 and derives Argon2d and Argon2id keys with hash-wasm, both pinned. The page hands it the file, the password and any key file, moved rather than copied. It answers with the entries as KeePass XML, held in memory, which the import reads as it reads an XML export. Attachments come beside it, as bytes moved to the page rather than base64 in it, and those over the instance's file limit come with only their name and size. Custom icons are left out. An XML export's attachments are unpacked on the page, within the same limit as a database's. Each database gets a fresh worker, ended when it answers, when you cancel, when the import closes, or after five minutes.
    - The database sets the work. The page reads its key settings from the header before asking for the password, and the worker reads them again before deriving anything. Both refuse more than 1 GiB of Argon2 memory, 100 passes, 16 lanes or 200 million AES-KDF rounds, and files over 100 MB. The Argon2 function checks the settings again with what it's actually asked for.
    - The database also sets what it unpacks to: GZIP says so in its last four bytes, and a small file can claim gigabytes, which would take the whole tab down, since a worker shares the tab's memory. kdbxweb is patched (`patches/kdbxweb@2.1.1.patch`) so that every GZIP stream it unpacks, the content and any attachment compressed inside it, is checked against what's left of 256 MiB for that database before anything is allocated.
    - A key file is read as KeePass reads one: a KeePass XML key file's key, its check verified when it has one; 32 bytes as they are; 64 hex characters; or else the SHA-256 of the whole file. Key files over 32 MB are refused. With a key file and no password, the key is tried without a password and then with an empty one, as KeePassXC does.
    - kdbxweb's XML parser, `@xmldom/xmldom`, is overridden to 0.8.15 in the root `package.json`, past the advisories on the 0.7 line kdbxweb asks for.
- **Backups protected with a password.** By default, **Download a backup** makes Bitwarden's password-protected export, built the way Bitwarden builds it, so vauly and Bitwarden both open it. Its key comes from a password you choose for the backup. Neither the password nor the key is sent anywhere or kept.
  - **The key.** vauly uses its own settings: Argon2id from hash-wasm, in the key worker, with 64 MiB, three passes, one lane and a fresh 16-byte salt. The steps above turn the result into the AES-256-CBC and HMAC-SHA256 keys.
  - **Guessing.** Anyone with the file can try passwords as fast as their hardware allows, and it holds every item you can open, shared vaults included. So the backup password must be as strong as a master password: at least 12 characters, and not easy to guess. The app offers a six-word passphrase.
  - **Not the master password.** The backup's key costs as much to guess as the master password's. A backup sealed with the master password would let anyone holding it test guesses at your account, so vauly refuses it.
  - **Files.** A backup with files is a ZIP: the export, plus each file at `files/<n>`, encrypted the way Bitwarden encrypts an attachment, with a random key of its own. Only the export, encrypted, holds the files' names, keys, sizes and SHA-256s.
    - The export's key encrypts no file, so no file can pass for the export, or for another file.
    - vauly unpacks only the files the export lists, each only at the size the export gives it. A backup with a file missing, or one that doesn't match, is refused.
  - **What it shows without the password.** That it's a vauly backup (its name and the `vauly` marker), its key settings and salt, the number of files, and each one's size, rounded up to 16 bytes. The ZIP also records when the backup was made.
  - **What it holds.** Every item you can open with its fields, tags and earlier passwords, which the CSV leaves out, and the files. Not passkeys. When it's imported, who changed each earlier password is left out, so a file can't put a teammate's name on a change.
  - **Without the password** a backup is a CSV, or a ZIP of the CSV and the files, all in plain text.

## Formats

Another implementation, such as a native app, must produce exactly these bytes. [`packages/crypto/test-vectors.json`](../packages/crypto/test-vectors.json) has made-up inputs and the expected output of each step below, intermediate values included, and the unit tests check `packages/crypto` against it. `bun run vectors` in `packages/crypto` regenerates the file from the formats as described here.
- **Text.** Bytes are standard base64 with padding, unless noted. The auth key is lowercase hex.
- **Master keys.** The password is normalized to NFKC and encoded as UTF-8. With `kdf` set to `argon2id`, Argon2id version 1.3 with the account's salt (16 random bytes, stored as `kdfSalt`), `kdfPasses` passes (3), `kdfMemory` KiB of memory (65,536), one lane, and no secret or associated data gives a 32-byte master key; `kdfIterations` is 600,000 and unused. With `pbkdf2`, PBKDF2-HMAC-SHA256 with the salt and `kdfIterations` rounds (600,000) gives it instead; accounts stored without a `kdf` are PBKDF2. HKDF-SHA256, with 32 zero bytes as salt and the ASCII info `vauly/auth` or `vauly/wrap`, turns it into the 32-byte auth key and the wrap key.
- **Sealed values.** AES-256-GCM with a random 12-byte IV, no additional data and a 16-byte tag after the ciphertext, written as `base64(iv) + "." + base64(ciphertext ‖ tag)`. An item is the UTF-8 JSON of its fields, sealed with its item key.
- **Data keys.** Vault and item keys are 32 random bytes. A key wrapped with another key is those 32 bytes, sealed.
- **Key pairs.** ECDH on P-256. Public keys are DER SubjectPublicKeyInfo; private keys are DER PKCS#8. The account's PKCS#8 private key, sealed with the wrap key, is `encryptedPrivateKey`.
- **Wrapping to a public key.** A fresh P-256 key pair, then ECDH with the recipient's public key (the 32-byte x coordinate). HKDF-SHA256, with 32 zero bytes as salt and the info `vauly/share:` followed by the recipient's public key in base64, gives an AES-256-GCM key. The result is `base64(ephemeral public key) + ":" + ` the data key sealed with it.
- **Share links.** The link key is 32 bytes in base64url without padding, after the `#`.
- **Agent tokens.** `vauly_agent_<id>.<secret>.<private key>`: the secret is 24 random bytes in hex, and the private key is PKCS#8 in base64 with `+` and `/` replaced by `-` and `_` (padding kept). The server stores the SHA-256 of the secret, in hex.
- **One-time codes.** RFC 6238 with base32 setup keys, or `otpauth://` links.
- **Passkeys.** A passkey's PKCS#8 private key is sealed with its vault's key, with the additional data `vauly/passkey` and the passkey's credential ID (base64url without padding) on a line of its own, and kept as `sealedKey` in the item's `passkey` field.
- **Device copies.** The key is HKDF-SHA256 of the passkey's 32-byte PRF output, with the server's 32-byte pepper as salt and the info `vauly/device`. It seals the PKCS#8 private key with the additional data `vauly/device`, the account ID, the passkey's ID (base64url) and the public key, each on a line of its own. The pepper is HMAC-SHA256 of `device:<session ID>:<issued at, in milliseconds>`, keyed with the server's secret.
- **Files.** A file's `meta` is the UTF-8 JSON `{ v: 1, name, type, size, chunks, key }`, where `key` is the file key's 32 bytes and `chunks` is the size divided by 1,048,576, rounded up, and at least 1. It's sealed with the item key, with the additional data `vauly/file-meta`, the file's ID and the item's ID, each on a line of its own. The contents are split into chunks of 1,048,576 bytes, the last shorter (an empty file is one empty chunk). Chunk `i` of `n` is AES-256-GCM under the file key with a 12-byte nonce of four zero bytes and `i` as a big-endian 64-bit number, the additional data `vauly/file`, the file ID, `i` and `n`, each on a line of its own, and a 16-byte tag. It's stored as `base64(ciphertext ‖ tag)`, with no IV, since the nonce comes from `i`. A file key encrypts one file only, so no nonce repeats under a key. The test vectors give a small file's sealed chunks whole, and a big file's as the SHA-256 of each chunk's base64 text.
- **Protected backups.** Bitwarden's password-protected JSON:
  - **Its fields.** `encrypted` and `passwordProtected` are true and `vauly` is 1. `salt` is 16 random bytes in base64. Then `kdfType` 1, `kdfIterations` 3, `kdfMemory` 64 (in MiB) and `kdfParallelism` 1.
  - **The key.** Argon2id version 1.3, salted with the SHA-256 of the salt's base64 text, gives 32 bytes. HKDF-Expand with SHA-256 and the infos `enc` and `mac` turns them into a 32-byte AES-256-CBC key and a 32-byte HMAC-SHA256 key.
  - **The encrypted parts.** `encKeyValidation_DO_NOT_EDIT` holds a random UUID and `data` holds the export. Each is `2.` followed by `base64(iv)|base64(ciphertext)|base64(mac)`: a fresh 16-byte IV, PKCS#7 padding, and the MAC over iv ‖ ciphertext.
  - **The export.** `data` is Bitwarden's plain JSON export, with `vauly` 1 at the top and a `vauly` object on each item: the item as vauly holds it. An item's `vauly.files` lists its files as `files/<n>/<name>`. With files, `vaulyFiles` at the top maps each `files/<n>` to `{ key, size, sha256 }`: the file's key (64 random bytes, the AES-256-CBC key then the HMAC-SHA256 key, in base64), its size before it was encrypted, and the SHA-256 of its contents, in base64.
  - **With files,** the ZIP holds the export as `vauly-backup-<date>.json`, and each file at `files/<n>` as the byte 2, the IV, the MAC, then the ciphertext: AES-256-CBC under the file's key, with a fresh IV, and HMAC-SHA256 over iv ‖ ciphertext.
- **Offline copies.** A JSON object of the vaults list, the items list, the files list (all three as the API returns them; a file's `meta`, never its contents) and the profile, sealed like any other value with a new 32-byte key. That key is wrapped to the account's own public key the way a vault key is wrapped to a member's. Stored beside it, in the clear: the account ID, the session ID, when it was synced, and the account's key derivation settings and salt, public key and sealed private key.

- **Build manifests.** `/.well-known/vauly-build.json` lists every file the web app's build serves, each with its SHA-256 in hex, and the commit it was built from. It also gives, for each rule in `_headers`, the headers its files are served with (every page's, and the key worker's), and the instance's settings that the app reads from `/vauly.json`. Those two files and `_headers` hold settings, not code, so they aren't hashed.

## Unlocking with a passkey

On a device where you turn on **Settings › Unlock with this device**, vauly unlocks with Face ID, Touch ID, Windows Hello or the device's PIN instead of the master password, for 14 days at a time. It works only in browsers whose passkeys support the WebAuthn PRF extension, and vauly doesn't offer it anywhere else.
- **Turning it on** asks for the master password first. Then the browser creates a passkey for your vauly's address, which needs the device to verify you. Given a random 32-byte salt, the passkey's PRF extension returns a secret that only that passkey can produce, and only after that check. The server adds a pepper: an HMAC, under its own secret, of this session and of when the copy was made. HKDF-SHA256 turns the two into an AES-256-GCM key, which seals a copy of your private key. The copy's additional data names the account, the passkey and the public key, so it opens for nothing else, and the key inside is checked against your public key before it's used.
- **This device keeps** the sealed copy, the passkey's ID, the salt, your public key, the session's ID and when the copy was made, in IndexedDB. The PRF secret, the pepper and the key made from them are never stored. The server never sees the passkey or anything it produces, and it keeps nothing new: it can recompute the pepper, but without the passkey that opens nothing.
- **Unlocking** asks for the passkey, then for the pepper, which the server hands out only inside the session the copy was made in, and only for 14 days after it was made. It happens only on the unlock screen. Signing in on a device still needs the master password.
- **Ending it.** Once the session ends, by a sign-out here or on another device, by **Settings › Where you're signed in**, by an admin removing you or by the session running out, the server can't give the pepper any more, so the copy can't be opened, even by someone who copied the device's storage. After 14 days the server refuses it as well. Separately, the device deletes the copy when it next starts without that session, when you turn it off, sign out or change your master password there, and when a copy fails to open.

On that device, for those 14 days, the passkey stands in for the master password: someone who has the device, or a copy of its storage while the session lasts, and who can pass its check (your face, your fingerprint, or the device's PIN or password) can unlock. If the passkey syncs, as in iCloud Keychain or Google Password Manager, so can someone who controls that account and also has the device's storage while the session lasts. Your key pair never changes, not even with a new master password, so what someone opens that way stays open to them; sign the session out to end it. Turn this on only on devices whose PIN or password you keep to yourself.

## Offline copy

So the installed app can open items without a connection, each device keeps a copy of what the API last returned for you: your vaults with their wrapped keys, and your items' ciphertext. Members, activity and share links aren't kept. Turn it off under **Settings › Offline copy**, which deletes it.
- **It's sealed whole**, with a key wrapped to your own public key, so even its item and vault IDs and timestamps need your master password. Only what unlocking needs stays readable: the KDF salt and iteration count and your sealed private key, the same as the server keeps, with your account and session IDs and when it was synced. Nothing decrypted is ever written to storage.
- **Offline, it's read-only.** The master password unlocks it; unlocking with a passkey needs the server, so it doesn't work offline. Adding, editing, sharing and approvals wait for a connection, and copies and reveals made offline aren't recorded in the activity log.
- **It belongs to the session it was made in.** The device deletes it when it next starts without that session, after any sign-out from this device or another, or a removal, and when you sign out, change your master password there or turn it off. Every sync rewrites it from what the API returns, so a vault you lose access to leaves it then.
- **It's used for 30 days at most** after its last sync, then deleted. That limit is enforced by the app, not by cryptography: a device offline has no trusted clock.

## Notifications

A device where you turn on **Settings › Notifications** is told when an agent asks for an item you can approve, when your account signs in somewhere new, and when two-step login is turned on for your account. An owner's or admin's devices are also told when anyone in the workspace sets up two-step login. They use Web Push.
- **What a notification says.** It gives the agent's name and how many items it asked for, the browser and system that signed in or turned on two-step login ("Chrome on macOS"), or who set up two-step login. It never names an item or a vault: the server can't read those. Tapping it opens vauly, and approves nothing.
- **Who can read it.** The server encrypts each notification to the device's own key (RFC 8291, `aes128gcm`) before it hands it to the browser's push service: Google's, Mozilla's, Apple's or Microsoft's. The push service sees which device it's for and when, but not what it says. Every push is padded to the same size, so its length doesn't give away an agent's name. Its headers do say how urgent it is and how long to keep trying, so the push service can tell a request for approval from a sign-in. Your device's system shows it, so anyone who can see your lock screen can read it, and the system may keep it.
- **Signed by the server.** Each push carries a VAPID signature (RFC 8292). It's made with a P-256 key pair that the server creates the first time a device turns notifications on, and keeps in its database, like the session secret.
- **Only to push services.** The server sends only to the push services of those browsers, over HTTPS, and doesn't follow redirects, so nobody can make it post to an address of their choosing. An address already in use for someone else's sign-in is refused.
- **Limits.**
  - Each session has at most one device, and each person at most ten.
  - An agent's requests send notifications at most once every five minutes, so a stolen agent token can't keep phones buzzing. Requests in between wait in the app.
  - One event sends at most 25 pushes, so a large team stays within a Worker's limits. Each person's newest device is first.
- **It belongs to the session.** These stop notifications to a device:
  - signing out, on that device or from another one;
  - being removed from the workspace;
  - the session running out;
  - its push service saying the device is gone;
  - three sends to it failing in a row.

  Turning on two-step login signs out your other sessions, and their devices still hear about it: the server reads them before it signs them out, and tells them which device turned it on.
- **iPhone and iPad.** Only the app added to the Home Screen gets notifications, on iOS 16.4 or later.

## Agents and scripts

An agent's key pair is created in the browser. Its private key goes into the token, which is shown once and never stored by vauly; the server keeps the public key and a SHA-256 hash of the token's secret. When a person approves a request, their browser wraps that item's key to the agent's public key. `vauly run` decrypts the item on the machine where it runs, passes the value to the command in its environment, and masks the value in the command's output. See [Agents and scripts](agents.md).

Anyone who holds an agent token can use whatever that agent has been allowed to use. An agent acts for the person who created it, so it can only use items in vaults they can open: it stops working when they leave the workspace, loses its grants in a vault when they lose that vault, and loses an item that's moved to a vault they can't open. An item can't be granted to an agent whose owner can't open its vault. Treat a token like a password, give each agent only the items it needs, and pause or delete agents you no longer use.

## Browser extension

The extension signs in with the same auth key as the web app and keeps the session token in its own storage, sending it as a bearer token. Like the web app's cookie, the token carries a signature with the server's secret: the bare token, as the database stores it, opens no session. The API accepts sign-ins from `chrome-extension://` and `moz-extension://` origins for this, since each install has its own ID. The unlocked private key is kept only in the extension's session storage, which lives in memory, can't be read by pages or content scripts, and is cleared when the browser closes or after 15 idle minutes. Filling runs a small script in the page only when you choose a login to fill, and that script first checks the page is still the one the login was chosen for. What vauly adds to a site's page doesn't depend on what the vaults hold, so the page learns nothing about them before you act. Its button shows in any login field while the extension is set up. The fill menu it opens is an iframe of the extension's own page, which the site can't read. The menu is the same size whatever it lists, and it closes through the extension rather than by messaging the page. Both sit in closed shadow roots. A site that framed the menu's page itself would get nothing from it: for each menu it opens, the page script gets a one-time token from the extension and puts it in that frame's address, and the extension answers only the first frame to show the token, in that tab and that document, until the menu closes. Where the browser allows it, the menu's address also has an ID that changes every session (`use_dynamic_url`). The menu lists only logins saved for the page's own host: the same name and port, with or without a `www.` in front of a name that is a site of its own. It never receives a password. The popup also lists logins saved for other hosts of the same site, by the Public Suffix List, naming each. A login saved with `https://` is never offered on an `http://` page. The offer to save a login opens in a window of vauly's own, beside the page (and, except in Firefox, without taking the focus), so whether it shows, and whether it offers to save or to update, stays out of the page. It offers to update only a login saved for that very host; on another host of the site, it offers a new login. To offer saving new logins, a content script on each page reads the username and password of a sign-in form when it's submitted and hands them to the extension, which keeps them in session storage for that tab for five minutes at most. Submissions on your vauly server's own pages are dropped, so the master password is never held. See [Browser extension](browser-extension.md).

A page could try to get a click on a login in the menu while hiding the menu, or showing something else over it. vauly's button and menu take their styles as `!important`, and changes a page makes to them are undone. While the menu is open, the page script also checks what's around it, on every frame the browser draws and after every change to the page: `<html>`'s opacity, filters, masks, clipping, transforms, zoom and blending; anything drawn from `<html>` itself or added to it after the menu; anything in the top layer, such as a popover, a modal dialog or a full-screen element; and whether the menu is still where vauly put it, at its size. The menu closes when it finds any of these, and the extension checks once more before it fills. A menu that opens on a page already doing one of these says it won't fill. A click on a login counts only once the logins have shown for half a second and the pointer has moved over the menu since. In Chrome, the browser must also report the menu as visible, not covered, faded or distorted, for that half second unbroken, and the wait starts over whenever it isn't. These checks can't see everything a script running on the site itself could do. Chrome's report covers much of what they miss; Firefox can't report whether the menu is visible, so there the protection is weaker, and the toolbar popup is the safer way to fill on a site you don't trust.

## Passkeys

The extension makes and uses passkeys (WebAuthn credentials) for the sites you sign in to. Each one is an ES256 key pair (ECDSA on P-256) made with WebCrypto in the extension. Its credential ID (16 random bytes), the site's relying party ID and the user handle go into a login item, under `passkey`, encrypted with the item's key like its password. The private key (PKCS#8) is sealed again, with the key of the vault the item is in (see [Formats](#formats)), so it opens for the people who can open the vault. An agent given the item gets only the item's key: it can use the password, never the passkey. Moving the item to another vault seals the private key again for that vault.
- **Which site can ask.** A script that starts with every HTTPS page (and `localhost`) passes the site's calls to `navigator.credentials.create()` and `get()` to the extension; it holds no keys. The extension takes the page's origin from the browser, never from the page, answers only the top frame of a page with an origin of its own (not a sandboxed one), and sends the answer only to the document that asked. A page at an IP address can't use passkeys. The relying party ID must be the page's own host or a parent of it, and never a public suffix such as `github.io`, checked against the Public Suffix List. A passkey is offered only for the relying party ID it was made for.
- **vauly asks in a window of its own.** Nothing is made or signed until you choose in it. It's an extension page that sites can't open, frame, cover or click in, and it opens for every passkey request while the extension is signed in, before vauly looks at your vaults. The page learns nothing about what vauly holds until you choose. Closing the window, Escape, **Cancel** or the site's own timeout (between 30 seconds and 10 minutes) turns the request down. Everything vauly doesn't handle goes to the browser's own passkeys with the site's options untouched: **Use another way**, requests while the extension isn't signed in, on your vauly's own pages or with passkeys turned off (everywhere, or for that site), algorithms other than ES256, security keys, the PRF and large-blob extensions, conditional sign-in and requests from embedded frames.
- **Present and verified.** Choosing in the window is user presence. User verification is the master password: unless the site says verification is discouraged, it must have been entered in the last 5 minutes, when unlocking or in the window itself, or the window asks for it. Only then does the passkey say you were verified.
- **What a site gets.** Attestation is always `none`, with an all-zero AAGUID. The flags say the passkey is backup-eligible and backed up, since it syncs with the vault, and its only transport is `internal`. The signature counter stays 0, as with other synced passkeys, so signing in never writes to the item, and a passkey in a vault someone can only view works for them too. Each sign-in is recorded in the activity log.
- **A passkey in a shared vault is the team's,** like a password. Taking someone out of the vault doesn't take back what they could have copied while they had it, and the Overview's list of items they could see covers passwords, not passkeys. vauly can't replace a passkey yet: remove it at the site and make a new one.

## The app for iPhone

The vauly app for iPhone, not in the App Store yet, runs this web app in a WebView, from files built into the app, and connects to the vauly whose address you give it.
- **It holds its session as a bearer token, never a cookie.** The app's pages come from `capacitor://localhost` and your API from its own address, so to WebKit the session cookie would be another site's, and it keeps none. The app signs in with the same auth key as the web app. It keeps the session token the API gives it, signed as the cookie would be, in the iPhone's Keychain, readable only while the iPhone is unlocked and never restored to another device or synced, and sends it as a bearer token, as the browser extension does. Signing out, or the session ending on the server, deletes it. So does deleting the app: the Keychain outlives an app, so the app clears its items the first time it starts after an install. If the Keychain can't be read, as before an iPhone is first unlocked, the app says so rather than asking for a vauly again. The app's native logging is off, so what passes between the page and the app never reaches the device's log.
- **The token is within the page's reach**, unlike the web app's cookie, which no script can read. A script that got into the app's page could take the session, as it could read whatever you've unlocked. Its policy, below, is what stands in the way.
- **The API lets the app in on every deploy.** It answers CORS for `capacitor://localhost` without allowing credentials, so a page from that origin never sees the answer to a request that carried a cookie. No web page can have a `capacitor:` origin. Android's WebView uses `https://localhost`, which a page on someone's computer can have too, so the API doesn't let that in; the Android app needs an origin of its own first.
- **Every Capacitor app on a phone has that origin too.** Another app gets nothing from it that it couldn't get without it: an app can send any request it likes from native code, CORS or not, and what keeps it out is that it has neither your session nor your master password. It can't read the vauly app's Keychain items or its WebView's storage, which belong to the vauly app alone. One case would be different: someone who signed in to vauly's website in a browser built into another Capacitor app, whose own pages can then send that browser's cookies. The vauly app never sends a cookie, so a cookie never goes with that origin: the API refuses any request from it that carries one, however the origin is capitalized, and Better Auth trusts it only for a request that carries none, whether it's named in `Origin` or `Referer`, and never as where a sign-in may send you back to.
- **Why not native HTTP.** Capacitor can send the page's `fetch` through native code instead, outside CORS, which would have needed no change to the server. The app doesn't use it: those requests leave from native code, where the page's Content-Security-Policy doesn't reach, and the proxy behind it is open to any script in the page. It also gives `fetch` another network stack than the one the web app is tested on. So the app turns it off, and puts a plugin that refuses every call in place of Capacitor's HTTP plugin, which Capacitor registers in every app regardless. It does the same with Capacitor's WebView plugin, which can point the app at other files on the device: the app runs only the files it shipped with. Each refusing plugin is registered under the plugin's class name too, since Capacitor would otherwise load the real plugin when the page calls it by that name.
- **Its pages have a Content-Security-Policy too.** The app's own files come with no headers, so it's set in the page: the web app's policy, except that until you name your vauly it may connect to any `https://` address. A debug build serves a page whose policy also lets it reach a vauly on the same computer over plain http, for development; a release build's allows only https. Once the app knows your vauly, it adds a second policy, which a request must pass as well, that lets it connect only to that vauly, its API and, while the breach check is on, Have I Been Pwned. A policy set in the page doesn't reach workers, so in the app the key worker and the KeePass import worker have no policy of their own; they run only the app's own files.
- **Connecting** reads `/vauly.json` at the address you give, and at the API's address if it names another, before keeping it. Both must be `https://`, but for `localhost` in a debug build. An address that doesn't answer, one that answers but isn't a vauly, and a vauly that doesn't let the app in yet (before 0.3.0) each get a message of their own. The app keeps the API's address it found then, with the session, and talks to that API only: if your vauly's `vauly.json` later names another, the app sends nothing, to either, and shows both until you connect again. So whoever can change the files your vauly's address serves can't quietly send the app's sign-ins somewhere else.
- **Unlocking with a passkey isn't offered in the app.** A passkey belongs to a website's domain, which the app's pages don't have.

## Share links

A share link shows one item to someone outside the workspace. The sender's browser copies the item's username, password or value, website, notes and, only if asked, its one-time code secret, but never a passkey, then encrypts the copy with a new AES-256-GCM key. The server stores the ciphertext under a random link ID. The key goes into the link's `#fragment`, which browsers never send to a server, so the link ID alone opens nothing.

The recipient's page asks the server for the ciphertext only after they choose **Show the item**, which keeps link previews in chat apps from using up a one-view link. The server counts each opening in the same statement that checks the link's limits, refuses links that expired, were used up, or whose item is in Recently deleted, and records each opening in the activity log. Anyone who can open the item can see its links and turn them off.

A link is a copy: changing the item later doesn't change what the link shows, and anyone holding the full link can open it until it stops working. Send it the way you'd send the password itself.

## Website logos

To show a brand's logo next to an item, the browser loads an image from Brandfetch's CDN for that brand's domain. Only the registrable domain is used (`hubspot.com` for `app.hubspot.com`), never a subdomain, and never an IP address or a private network name such as `.local`, `.internal` or `.corp`. Items without a website get a logo only when their name matches a short list of well-known services. Brandfetch requires a `Referer`, so it also sees the address of your vauly, along with your IP address, like any image request. It learns nothing else about the item. Turn logos off per device in **Settings → Website logos**, in the browser extension's settings (the gear) with **Show website logos**, or for a whole instance by deploying with `VITE_BRANDFETCH_CLIENT_ID=off`, which the extension follows too.

## Breached passwords

To find passwords that turned up in data breaches, the browser asks Have I Been Pwned's [Pwned Passwords](https://haveibeenpwned.com/API/v3#PwnedPasswords) with k-anonymity. It works out the password's SHA-1 hash and sends only the first five hex characters. The service answers with every leaked hash that starts with them, about a thousand, padded with made-up entries so the answer's size gives nothing away, and the browser looks for the rest of the hash in that list. Have I Been Pwned never sees a password or a whole hash: the five characters it gets are shared by about a thousand leaked passwords, and by countless others. The requests carry no cookies and no `Referer`, so they don't say which vauly asked. Answers are kept in memory until vauly locks. Turn the check off per device in **Settings → Breached passwords**, or for a whole instance by deploying with `VITE_BREACH_CHECK=off`.

## How the app is served

The web app's pages come with a Content-Security-Policy that runs only the app's own script files: no inline scripts, nothing evaluated from a string, nothing from another site. The pages can connect only to your vauly API and, while the breach check is on, Have I Been Pwned, and load images only from the app itself and, while logos are on, Brandfetch's CDN. If a bug ever let someone slip markup into a page, the browser would neither run their script nor send what it read anywhere else. The app also refuses to be shown in a frame (`frame-ancestors 'none'`, and `X-Frame-Options: DENY` for older browsers), so another site can't hide it under a page of its own and trick you into clicking **Reveal** or **Share**. The one exception is the key worker's folder, which also holds the worker that opens KeePass databases: its policy lets them compile WebAssembly but not connect anywhere (see [Key derivation](#key-derivation)). The build writes these headers to a `_headers` file, which Cloudflare applies in both ways of deploying; see [`apps/web/security-headers.ts`](../apps/web/security-headers.ts).

## Checking what an instance serves

Your browser runs whatever JavaScript your vauly's address sends it, so the code that keeps your master password is only as trustworthy as the hosting it comes from. `vauly verify` lets anyone check that an instance serves exactly the web app its version builds, nothing changed and nothing added:

```sh
vauly verify https://vault.example.test
```

- **Every instance of a version serves the same files.** The app reads its address, logo and breach-check settings from `/vauly.json` at runtime, so the code can't differ between instances. Two builds of one commit are byte-identical, on any machine: CI builds it twice in different directories, and again on macOS, and compares. The service worker lists the files it caches sorted, not in the order a file system happens to hand them over.
- **Every build runs in Bun, the version in `package.json`.** The files depend on the JavaScript runtime that runs Vite: it copies one of its own functions into the app as source text, and Bun re-prints the source it loads, so a build under Node, or another Bun version, differs in every file. `bun run build`, the Deploy to Cloudflare button and `alchemy deploy` all build in Bun, and CI checks that Alchemy's build, with a stage's settings, serves the same files as `bun run build`. The manifest records the runtime, and `vauly verify` says so when the build it compares with ran in another.
- **Each build lists what it serves** in `/.well-known/vauly-build.json`: every file with its SHA-256, the headers it sets (the Content-Security-Policy among them), the commit and the runtime it was built in.
- **`vauly verify` downloads all of it.** It checks every file and header against that list, and it checks that the page and the service worker load nothing the list leaves out. Then it builds the same commit with the same settings itself and compares. That needs `git` and `bun`, the same version as the instance's for a match. `--against` instead compares with a manifest you trust, such as the one each release carries.

What it can't prove:
- **It shows what was served to you, just now.** A host can serve other files to other people, or to you at another time. A service worker your browser installed earlier keeps running what it was given until it updates.
- **It covers the web app, not the server.** The API Worker can't read what it stores, but it decides who gets what, hands out the public keys that keys are wrapped to (see [Limits](#limits)), and could serve another app later. Verify again when it matters.
- **A matching build means the files come from that commit and its locked dependencies.** It doesn't mean the source, or the dependencies, are free of mistakes.

## Limits

These are the things vauly does not protect against. Please read them before you rely on it.
- **The server delivers the app.** vauly runs in the browser, and the browser loads its code from your instance. Someone who controls the web app's hosting could ship code that captures your master password the next time you sign in. This holds for every web-based end-to-end encrypted app, and the Content-Security-Policy can't help, since the same hosting serves the policy. Host vauly yourself, keep your Cloudflare account secure, limit who can deploy to it, and use `vauly verify` (above) to check what it serves.
- **The server hands out public keys, and the apps don't check them yet.** To share a vault with a member, or give an agent an item, the app wraps the key to the public key the server says is theirs; a new vault's key is wrapped to your own public key, as the server gives it. Someone in full control of the server or its database could put a key of their own in place of a member's or an agent's, and open what's shared with that member or agent from then on. What was shared before stays out of their reach. Checking public keys is planned.
- **Requiring two-step login doesn't close the gap before someone sets it up.** Until a member has set it up, their password alone signs them in, and whoever does that first sets up the second step: someone who knows their password could add their own phone. Each setup is in the activity log, and admins hear about it on their devices if they turned notifications on, as do the member's own devices that it signed out. If it wasn't them, an admin resets the member's two-step login on the **Members** page, which signs them out everywhere, the other person too, and sends them back to set it up. They should then change their master password, since someone else knows it. A device with an offline copy can still open it with the master password, as the next point says.
- **A device that stays offline keeps its offline copy.** Signing a session out, removing someone or changing the master password reaches a device only when it next connects. Until then, someone with that device and the master password (an old one too, since the key pair doesn't change) can read the items it held at its last sync. Turn the offline copy off on devices you might lose.
- **Deleting an account deletes what only it could open.** Someone who deletes their account takes their private vault and agents with them, and any shared vault nobody else could open; those are gone for everyone, as nobody holds their keys anymore. Shared vaults others can open stay, and the activity log keeps their name. See [Self-hosting](self-hosting.md#when-someone-deletes-their-account).
- **Removing someone doesn't take back what they've seen.** Taking a person out of a vault deletes their copy of its key, so they can't open it through vauly again. But they may have copied passwords, or the vault key, while they had access. Change the passwords that matter after someone leaves: the Overview lists the items they could see that haven't changed since.
- **Nobody can reset a master password.** It, and for up to 14 days a passkey on a device where you turned that on, are the only keys to your private key. If you forget the master password, your items can't be recovered by you, an admin or the server. An admin can invite you again so you start over.
- **A compromised device is out of scope.** Malware on your computer can read what you can read while vauly is unlocked.
- **One-time codes live next to passwords.** Storing a TOTP secret in the same item as the password is convenient, but it means the item alone is enough to sign in.
- **Metadata isn't hidden.** See the table above: the server knows who is in the workspace, who can open which vault, and when items are used.
- **No independent audit yet.** The design is small and the code is open, but it hasn't been reviewed by a third party.
